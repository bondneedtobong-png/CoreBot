## Сквозная платформа — текущие пробелы

| Контракт | Статус | Реализация / следующий шаг |
|---|---|---|
| Аккаунт + SOCKS5 + один владелец сессии | **частично** | `Worker`, `SessionLease`, прокси-пулы; проверить все новые операции через эту аренду |
| Источник цели → валидация → preview → снимок целей | **частично** | Рассылка фиксирует разрешённых клиентов и хеш конфига при постановке команды; парсер хранит результаты. Требуются типизированный конструктор и ошибки строк для других источников/модулей |
| Право на контакт, suppression/отписка | **частично** | `client_contact_permissions` и `bl/stop` проверяются для обычной рассылки до запуска и перед отправкой; требуется единый механизм для всех будущих коммуникационных модулей |
| Общее задание/версия/пресет/расписание | **частично** | ЛС-рассылка теперь имеет снимок, дату старта, отмену и восстановление; `parsing_tasks` и прочие команды пока имеют разные жизненные циклы |
| Общий gate, ограничения и история | **частично** | `reserve_send` покрывает текст и реакции прогрева, read-действия прогрева проверяют остановку; есть область чата для slow mode и свежая проверка перед resume. Нужно распространить на остальные будущие действия и все типы сигналов |
| Панель → очередь → worker → результат | **частично** | Работает для ручного ответа и AI-черновика; переносить контракт на новые модули |

## Этапы реализации и критерии

1. **Безопасность аккаунта и арбитр.** Дополнить `AccountSafetyState/Event` временем и областью ограничения; сериализовать исходящие действия одного worker; классифицировать FloodWait, slow mode, auth и сетевые ошибки; вынести факт/причину в панель. Проверка: два конкурентных действия после FloodWait не отправляют второй RPC, cooldown сохраняется после рестарта, slow mode затрагивает только один чат. Далее распространить gate на реакции/истории/вступления и другие новые действия.
2. **Цели и задания.** Через существующую БД и команды добавить источник целей с provenance, preview, дедупликацию, consent/suppression, версию конфига, расписание, отмену, восстановление. Проверка: импорт ошибочных/дублированных строк, неизменный снимок целей, отказ от ЛС без права на контакт.
3. **Аккаунты, прокси, парсеры и база площадок.** Довести подпункты 3.1–3.4, 3.16: массовые операции, health, индекс площадок, похожие/фильтры/экспорт. Проверка: тестовая группа и пул, история происхождения, повторный импорт без дублей.
4. **Коммуникация и AI.** Довести 3.5–3.9, 3.13: ЛС-цепочки, кампании своих чатов, inbox, управляемые AI-сценарии, аудит отправок. Проверка каждого режима на собственном тестовом адресате/сообществе и crash recovery для очереди.
5. **Истории, реакции, прогрев.** Довести 3.10–3.12 и 3.14 с явным правом на цель и общим gate. Проверка preview, дедупликации, остановки, недоступной истории, ограничения аккаунта.
6. **GGR и аналитика.** Довести 3.2 и сквозные экраны: наблюдаемые health-сигналы, история проверок, объяснимый показатель и экспорт. Проверка повторной проверки и расчёта по реальным локальным данным; без обещания прогноза банов.

Реестр остаётся открытым, пока каждый подпункт не получит настройку, preview, выполнение/остановку, результат и историю с тестом. Живые Telegram-проверки выполняются только на контролируемых аккаунтах и целях владельца.

### Выполнение в этом рабочем дереве

- Этап 1, часть: сериализация отправок одного worker; постоянный срок FloodWait; отдельный cooldown чата при slow mode; остановка при невалидной авторизации; панель показывает срок и область. Миграция сохраняет старые события. Проверки: `tests/test_account_safety.py`.
- Этап 2, часть: отдельное разрешение на контакт с источником и журналом, обязательная проверка в обычной и тестовой рассылке, preview перед запуском и повторная проверка перед Telegram RPC. Проверки: `tests/test_mailing_permissions.py`.
- В рамках второго этапа исправлено размещение формы тестовых получателей: она была в карточке клиента, а обработчик работал в карточке рассылки.
- Этап 3, часть: локальный поиск по сохранённым каналам и группам через `/business/parsing/catalog/search` с типом, языком, размером, активностью, комментариями, источником и временем проверки. Проверка: `tests/test_catalog_search.py`; поиск не открывает Telegram-сессию.
- Этап 2, часть: `mailing_runs` и `mailing_run_recipients` фиксируют адресатов и хеш настроек при фактическом старте, список запусков и счётчики доступны в панели; новые CRM-записи не входят в текущий запуск, а отзыв разрешения исключает адресата. После рестарта незавершённый запуск помечается `interrupted` без повторной отправки. Проверка: `tests/test_mailing_run_snapshot.py`. Для неопределённых исходов нужна ручная сверка с Telegram перед новым запуском.
- Этап 3, часть: похожие каналы/группы из локальной базы по общим словам названия с объяснимой оценкой и без Telegram-сессии. Проверка: `tests/test_catalog_search.py`. Это поиск по метаданным, не тематическая рекомендация или ИИ.
- Этап 3, часть: пользовательские папки площадок через `catalog_folders`/`catalog_folder_entries` с просмотром, добавлением/удалением и CSV для Excel в панели; повторное добавление идемпотентно, формулы в CSV экранируются. Проверка: `tests/test_catalog_search.py`.
- Этап 6, часть: `/business/account-safety/{id}/health` показывает локальную готовность 1–10 с явными вычетами и наблюдаемые события/отправки за 7/30 дней. Проверка: `tests/test_account_safety.py`. Это расчёт по БД CoreBot, без живой Telegram-проверки и прогноза блокировок.
- Этап 1, дополнение: реакции прогрева резервируют общий бюджет под блокировкой Worker, пустая цель не расходует попытку; read-действия проходят gate. Возобновление теперь ставится в `bot_commands`: бот проверяет назначенный SOCKS5 и свежую авторизацию, затем атомарно открывает gate. Неудача/прерывание оставляет аккаунт остановленным. Проверки: `tests/test_warmup_safety.py`, `tests/test_account_safety_resume.py`.
- Этап 5, часть: бот даёт выбрать один активный аккаунт и прямую ссылку на сообщение своего канала или супергруппы, проверяет права администратора и наличие сообщения, показывает preview, затем после подтверждения резервирует общую дневную попытку и отправляет одну реакцию. `managed_reaction_attempts` фиксирует попытку до RPC и запрещает повтор при неопределённом результате; последние попытки видны в меню. Проверки на подставном Telethon: `tests/test_managed_reactions_service.py`, `tests/test_managed_reactions_menu.py`. Живой Telegram вызов для этого сценария пока не выполнялся.
- Этап 4, дополнение: общий inbox загружает по 50 строк через `GET /business/dialogs?offset=…`, показывает «Показать ещё», очищает курсор при смене фильтра/аккаунта и обновляет уже загруженные страницы по SSE. Проверки: `tests/test_global_dialog_inbox.py`, `tests/dialog_global_inbox.cjs`. Offset ограничен 10000; запрос всё ещё группирует сохранённые сообщения, поэтому для большой БД нужны материализованная сводка диалогов и индекс поиска.
- Этап 3/16, часть: в управлении аккаунтами бот проверяет одну или до 20 публичных ссылок `t.me/username` через выбранный активный аккаунт без отправки и вступления. Пакет принимает сообщение либо UTF-8 `.txt`, показывает ошибки строк и повторы до подтверждения. Немедленная проверка останавливается между ссылками по кнопке; отложенная использует существующий `BotCommand.not_before`, сохраняет прогресс после каждой ссылки, поддерживает отмену и восстановление после перезапуска без нового цикла. Возможен повтор одного чтения при сбое между Telegram RPC и checkpoint. Сведения показываются только при подтверждённом admin-доступе; каждая корректная завершённая попытка попадает в `community_link_checks`, а история бота ограничена автором проверки. Прочие цели получают единый отказ без раскрытия статуса человека/чужого сообщества. Проверки на подставном Telethon и SQLite: `tests/test_community_link_checker.py`, `tests/test_community_link_check_menu.py`, `tests/test_community_link_batch_jobs.py`. Живая проверка собственного публичного сообщества ещё нужна; локальный аккаунт #7 не имел такого сообщества среди доступных диалогов.
- Этап 6, часть: TData ZIP и Telethon `.session` precheck до импорта сохраняют ограниченный отчёт в `tdata_check_history`; список последних запусков и подробности переживают перезапуск и доступны только запустившему оператору. `.session` ограничена 16 МиБ, её SQLite-структура проверяется до сетевого вызова, а работа идёт только с удаляемой временной копией через TDATA_CHECK proxy pool. В БД не попадают ZIP, auth key, пути к TData/сессии, прокси и сырой текст исключений; сохранение предшествует успешному ответу API. Панель открывает сохранённый отчёт по ID. Проверки: `tests/test_tdata_check.py`, `tests/tdata_check_history_ui.cjs`, `tests/session_precheck_ui.cjs`. Живой precheck существующего `.session` не запускали, чтобы не дублировать действующий auth key.
