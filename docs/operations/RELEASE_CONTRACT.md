# Релизный контракт CoreBot

## 1. Идентификация версии

- Версия приложения = полный git SHA коммита плюс тег, если он выставлен
  (формат записи: `<tag> (<sha12>)`, например `v1.4.0 (a1b2c3d4e5f6)`;
  без тега — только `<sha12>`).
- Источник установки фиксируется в учётной карточке инстанса
  (RUNBOOK, раздел 3): поле `corebot_version` обязательно.
- Установка из архива без git-метаданных допускается только при наличии
  файла `VERSION` в корне архива с тем же форматом; иначе версия
  считается неизвестной и инстанс — неподдерживаемым до переустановки
  из помеченного источника.

## 2. Совместимость

- Python: `3.11` или новее. На Ubuntu 22.04 при `python3 < 3.11`
  Python 3.11 ставится из `ppa:deadsnakes/ppa`.
- ОС: только Ubuntu `22.04 LTS` и `24.04 LTS`.
  Другие дистрибутивы и выпуски не поддерживаются.
- Стек инстанса: `venv` (`/opt/corebot/venv`) + `systemd`
  (`corebot.service`, `corebot-cp.service`) + SQLite (WAL).
  Переход на PostgreSQL и центральную SaaS-панель вне области
  настоящего контракта.
- Control Plane слушает только `127.0.0.1:8081`;
  релиз, требующий другого bind по умолчанию, к установке не допускается.

## 3. Порядок обновления (прямой путь)

Строго в этом порядке, остановка сервисов — не более 5 минут (см. SLO):

1. Остановить приём новой нагрузки: `systemctl stop corebot.service`.
   `corebot-cp.service` на время обновления остаётся запущенным,
   если инструкция релиза не требует иного.
2. Сделать бэкап (обязательно, см. раздел 4).
3. Обновить код: `git pull` конкретного SHA/тега
   (обновление «на последний master без фиксации SHA» запрещено)
   либо распаковка помеченного архива поверх `/opt/corebot/app`
   без затрагивания `.env`, `data/`, `logs/`, `data/sessions/`.
4. Обновить зависимости:
   `/opt/corebot/venv/bin/pip install -r /opt/corebot/app/requirements.txt`.
5. Применить миграции БД: запуск выполняется автоматически
   при старте (`main.py` → `db.connect()`, Control Plane — миграции
   в `control_plane/main.py`). Ручные SQL-миграции — только если их
   явно описывает примечание к релизу, и всегда после бэкапа.
6. Проверить ровно один режим парсера:
   `PARSER_EMBEDDED=1` — отдельного parser-сервиса нет;
   `PARSER_EMBEDDED=0` — разрешён один процесс
   `python -m workers.parser_worker`.
7. Перезапустить: сначала `systemctl restart corebot-cp.service`,
   затем `systemctl restart corebot.service`.
8. Проверить: оба сервиса `active`,
   `curl --fail http://127.0.0.1:8081/health/live` и
   `curl --fail http://127.0.0.1:8081/health/ready` — HTTP 200
   в течение 3 минут, `/start` от `OWNER_ID` — ответ в течение 5 минут.
9. Записать новый `corebot_version` и дату в карточку инстанса.

Миграции БД — только вперёд (forward-only, авто-миграции SQLAlchemy).
Понижение схемы миграциями не выполняется; возврат на предыдущую
версию идёт через восстановление бэкапа (раздел 5).

## 4. Backup-before-update (обязательно)

- Перед каждым обновлением создаётся tar-архив в `/opt/corebot/backups/`:
  `.env`, `data/corebot.db`, `data/control_plane.db`, `data/sessions/`.
- Имя архива содержит метку UTC:
  `corebot-<YYYYMMDDTHHMMSSZ>.tar.gz`.
- Обновление без свежего бэкапа (созданного в рамках той же процедуры)
  запрещено. Отсутствие места под бэкап — основание остановить
  обновление до освобождения диска.
- Дополнительно действует ежедневный cron-бэкап тех же путей
  (RPO `<= 24 часа`, см. `SLO.md`).

## 5. Откат (rollback)

1. Остановить сервисы:
   `systemctl stop corebot.service corebot-cp.service`.
2. Вернуть код на предыдущий SHA/тег из карточки инстанса
   (`git reset --hard <prev-sha>` либо распаковка предыдущего
   помеченного архива).
3. Восстановить `.env` и `data/` из предобновленческого архива.
4. Переустановить зависимости под возвращённый код
   (`pip install -r requirements.txt`).
5. `chown -R corebot:corebot /opt/corebot/app`,
   `chmod 600 /opt/corebot/app/.env`.
6. Запустить сервисы в порядке из раздела 3, шаг 7,
   и выполнить проверки из шага 8.
7. Зафиксировать факт отката (предыдущая и возвращённая версии,
   причина) в карточке инстанса.

Целевое время отката на том же VPS — `<= 60 минут` (RTO, см. `SLO.md`).

## 6. Поддерживаемое окно версий

- Поддерживаются установленный релиз и один предыдущий релиз (`N`, `N-1`).
- Инстансы старше `N-1` обновляются в первую очередь и вне очереди
  при инциденте безопасности.
- Релизные примечания каждого релиза обязаны указывать:
  SHA/тег, минимальную версию Python, поддерживаемые выпуски Ubuntu,
  наличие миграций БД, флаг совместимости вперёд/назад данных.
