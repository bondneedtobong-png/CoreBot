# SLO инстанса CoreBot

Область: один изолированный VPS-инстанс (см. `INSTANCE_CONTRACT.md`).
Окно измерения для процентных целей — 30 календарных дней.
Все пороги ниже — числа; словесные оценки без чисел не применяются.

## 1. Доступность Control Bot (Telegram-опрос)

- Цель: `>= 99.5 %` за 30 дней (допустимый простой `<= 3 часа 36 минут`
  в месяц).
- Определение «доступен»: `systemctl is-active corebot.service` возвращает
  `active`, и бот отвечает на `/start` от `OWNER_ID` в течение 60 секунд.
- Измерение: `systemctl is-active` каждые 5 минут + еженедельная ручная
  проверка `/start` по RUNBOOK, раздел 6.

## 2. Доступность и готовность Control Plane

- Цель готовности: `>= 99.0 %` за 30 дней для `GET /health/ready`
  (допустимый простой `<= 7 часов 12 минут` в месяц).
- Определение «готов»: `GET http://127.0.0.1:8081/health/ready`
  возвращает HTTP 200 за `<= 2 секунд`.
- Дополнительно: p95 latency `/health/ready` — `<= 1 секунда`
  при опросе 1 раз в минуту с того же хоста.
- Неготовность сигнализируется кодом HTTP 503
  (недоступна БД Control Plane, БД бота, терминальный отказ парсинга
  или падение контролируемых фоновых задач).
- Лёгкие пробы `GET /health` и `GET /health/live` должны отвечать
  HTTP 200 за `<= 2 секунд`, когда процесс Control Plane запущен.

## 3. Бюджет простоя на обновление

- Одна процедура обновления: остановка сервисов — `<= 5 минут`,
  число перезапусков сервисов — `<= 2` (`corebot-cp.service`,
  затем `corebot.service`).
- Суммарный простой на обновления: `<= 30 минут` в календарный месяц.
- После рестарта: `/health/ready` — HTTP 200 в течение `<= 3 минут`,
  `/start` от `OWNER_ID` — ответ в течение `<= 5 минут`.

## 4. Цели восстановления данных

- RPO (максимальная потеря данных): `<= 24 часа`.
  Достигается ежедневным бэкапом `data/` и `.env` (cron, раз в сутки).
- RTO на том же VPS (отказ сервиса или неудачное обновление): `<= 60 минут`
  от обнаружения до `active` + `/health/ready` HTTP 200.
- RTO на новом VPS (потеря хоста, перенос по разделу 11.1 RUNBOOK):
  `<= 4 часа` от предоставления чистого VPS (Ubuntu 22.04/24.04)
  до `/start` + `/health/ready` HTTP 200.
- Состав бэкапа (минимум): `.env`, `data/corebot.db`,
  `data/control_plane.db`, `data/sessions/`.
- Проверка восстановления: не реже 1 раза в 90 дней —
  развёртывание бэкапа в пустой каталог и открытие обеих БД
  (`sqlite3 … "PRAGMA integrity_check;"` возвращает `ok`).

## 5. Обязательные алерты и пороги

| # | Сигнал | Порог срабатывания | Канал |
|---|--------|--------------------|-------|
| 1 | `corebot.service` не `active` | `> 2 минут` подряд | Telegram-алерты Control Plane + журнал |
| 2 | `corebot-cp.service` не `active` | `> 2 минут` подряд | Telegram-алерты Control Plane + журнал |
| 3 | `/health/ready` не 200 / HTTP 503 | `> 5 минут` подряд | Telegram-алерты Control Plane |
| 4 | Место на диске `/` или `/opt` | `> 80 %` предупреждение, `> 90 %` критический | Telegram-алерты + еженедельная проверка |
| 5 | Рост `data/corebot.db` | `> 2 ГБ` предупреждение, `> 5 ГБ` критический | еженедельная проверка `du -sh` |
| 6 | Возраст последнего бэкапа | `> 26 часов` | проверка cron-метки ежедневно |
| 7 | Ошибки FloodWait / авторизации Telethon в `logs/error.log` | `>= 10` за 1 час | разбор логов при еженедельном обходе |
| 8 | Неверный токен ingest (HTTP 401) при `CP_AGENT_ENABLED=1` | `>= 3` за 10 минут | Telegram-алерты + журнал |

Проверка алертов входит в еженедельный обход RUNBOOK
(раздел 9): статус сервисов, ошибки за 24 часа, размер `data/`,
свободное место, дата последнего бэкапа.

## 6. Что не является SLO

Ограничения Telegram API (FloodWait, блокировки аккаунтов),
доступность OpenRouter и задержки LLM, а также доступность сети
между оператором и VPS не входят в цели выше и учитываются
отдельно при разборе инцидентов.
