# ADR 0001: Оркестратор парка независимых VPS

- Статус: принято.
- Дата: 2026-09-22.
- Контекст: задача 07 (управление парком VPS). Каждый пользователь работает
  на собственном изолированном VPS (см. `INSTANCE_CONTRACT.md`).
  Нужен один способ накатывать установку, обновления, бэкапы и проверки
  на десятки независимых хостов без разрушения изоляции.

## Рассмотренные варианты

### A. Bash-скрипты по SSH

Прямые shell-скрипты (`scripts/install_corebot.sh`,
`scripts/verify_corebot.sh`, `scripts/backup_corebot.sh`), запускаемые
оператором вручную на каждом хосте.

Плюсы: ноль новых зависимостей, уже есть в репозитории и в скилле
`corebot-vps-deploy`, прозрачны для одного хоста.

Минусы: нет инвентаря хостов, нет идемпотентности и декларативного
состояния, каждый новый хост — ручная работа, дрейф конфигураций
между хостами не детектируется, секреты приходится раскладывать вручную.

### B. Ansible с control node (выбран)

Декларативные плейбуки, запускаемые с control node (WSL или Linux)
оператора по SSH. Инвентарь — один хост на пользователя.
Секреты — только через Ansible Vault либо внешний локальный vault;
хранение секретов в Git запрещено.

Плюсы: идемпотентные роли повторяют safety-контракт скилла
(не затирать `.env`/`data`/`logs`/`sessions`, fail-fast на пустых
Telegram-creds и `change-me`/`admin123`, loopback `127.0.0.1:8081`,
backup-before-update), инвентарь фиксирует модель
«один пользователь — один хост», Vault решает хранение секретов,
SSH без агентов на управляемых хостах.

Минусы: требуется control node с Ansible и дисциплина Vault-паролей;
начальная стоимость выше, чем у Bash.

### C. Центральный управляющий агент / SaaS-панель

Постоянный контроллер, опрашивающий или управляющий всеми VPS
из одной точки (или единая мультитенантная панель).

Плюсы: централизованный обзор парка.

Минусы: противоречит зафиксированной модели независимых инстансов
и выходит за границы задачи 01 (PostgreSQL-миграция и центральная
SaaS-панель явно исключены). Создаёт единую точку компрометации
всех пользовательских `.env`, БД и сессий; требует постоянно
открытых каналов управления к каждому VPS и отдельной hardening-истории.
Отклонён по архитектурным причинам, а не только по стоимости.

## Решение

Для задачи 07 используется вариант B: **Ansible с control node
(WSL/Linux оператора), секреты — Ansible Vault или внешний локальный
vault, секретов в Git нет**.

Требования к реализации в задаче 07:

1. Инвентарь: одна группа/хост на пользователя, без общих переменных
   с секретами в открытом виде.
2. Роли повторяют safety-контракт: backup-before-update, сохранение
   `.env`/`data`/`logs`/`sessions`, проверка `PARSER_EMBEDDED`,
   bind `127.0.0.1:8081`, отказ при пустых Telegram-creds и
   `change-me`/`admin123`, проверка `/health/ready` после применения.
3. Существующие Bash-скрипты остаются как низкоуровневые примитивы
   для одного хоста и ручного восстановления; оркестрация поверх них —
   Ansible, а не наоборот.
4. Vault-пароль хранится только локально у оператора (или в его
   менеджере секретов), никогда в репозитории.

## Последствия

- Задача 07 проектирует Ansible-инвентарь, роли и Vault-политику,
  а не центральный сервер.
- RUNBOOK и скилл `corebot-vps-deploy` остаются источником истины
  для шагов на одном хосте; Ansible их вызывает, а не дублирует логику.
- Аудит парка сводится к `ansible-playbook --check` плюс сверка
  карточек инстансов из RUNBOOK.
